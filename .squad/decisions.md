## Round 9 -- 2026-08-02T22:37:04-07:00 -- KV can stay device-resident, the proof ledger learns to name its own frame, and three fallback-detection witnesses get their extents stated separately

### 2026-08-02T22:37:04-07:00: Switch — device-resident KV is permitted by ORT; the obstacle is `transfer.rs`'s own "host staging is authoritative" invariant, and it is now a per-span flag (consolidated)

**By:** Switch (`switch-kv-round-trip-not-removable-by-binding`, `switch-ort-permits-device-resident-kv`, `switch-device-authority-is-per-span`) — three findings on the same question, in the order they happened, consolidated because the second explicitly supersedes the first's open question and the third is the fix the second's ruling required.

**Stage 1 — binding alone returns zeros.** Tank had shown `bind_target_for` is called on inputs only, so the unconditional output readback cannot be declined. Testing an output-side bind: ORT *does* place fused-node outputs in this EP's device memory when armed (0/195 → 195/195 device-resident, refuting "ORT forbids it" as originally framed), but the bound outputs (`logits`, `present.0.key`, `present.31.value`) came back **entirely zero**. `transfer.rs`'s own comment predicted it: *"the staging block stays authoritative … the device buffer is a mirror."* The kernel writes the device buffer; the caller reads the host block; nothing writes the host block. A first-cut scorer nearly certified the zero lane as a `BOUND_OUTPUT_IS_SOUND` win (an all-zero tensor scores 1.0 against a 1e-3 relative floor) — caught before publication: *"a scoring rule that can be beaten by returning nothing is not a scoring rule."*

**Stage 2 — the ruling.** A caller *can* bind an `OrtValue` in this EP's device memory as a graph output and get back bit-identical results to the unbound run (`KV_CAN_STAY_DEVICE_RESIDENT`), via `OrtEpDevice.memory_info(DEFAULT)` — the documented `ortvalue_from_shape_and_type(..., 'gpu', ...)` spelling fails because ORT 1.28's Python binding maps `device_type='gpu'` to CUDA even against our vendor id. So the project is **not** in the "ORT forbids it" world; the obstacle is entirely ours. Ordering is load-bearing: requesting the allocator before the session exists builds a second `VkDevice` (`SPLIT-DEVICE`) that no dispatch can reach, and the probe refused to report on it rather than publish numbers describing a device the kernels never ran on. Not claimed: the round trip is not yet removed, only shown removable.

**Stage 3 — the fix.** `transfer.rs` no longer holds one global rule about which copy of a span is real. Each span now carries `device_authoritative`, set by the engine only when a dispatch is about to write that span's device buffer directly — closing the gap Tank's KV re-decision (below) and Stage 1 both hit. Both devices measured `KV_CAN_STAY_DEVICE_RESIDENT` with all outputs nonzero and Phi-3.5-vs-CPU-EP passing. Still not claimed: the round trip is *moved*, not removed (paid and counted whenever a caller asks for host bytes — `1792 = 512+640+640` B/step on the resident lane vs. host-lane's per-step cost), the growing-context term beyond `past=4` is unmeasured, and no wall-clock figure is quoted (`PERF.md` §20, permanent contention). Two defects found only by running the case that was not already passing: a partial host write was revoking authority over a whole span (invisible on the common whole-span-write path), and `alloc_device_authoritative_spans` had two producers with different definitions summed into one counter — caught by its own control lane reading 1 with zero binds — split into `alloc_device_authority_grants`.

### 2026-08-02T22:37:04-07:00: Switch — a device loss that exits 0 is a smaller number, not a failure, and it needs its own counter (consolidated)

**By:** Switch (`switch-a-counters-file-is-not-evidence-of-work`, `switch-a-lost-device-that-exits-zero-is-a-smaller-number`) — same incident narrated at two stages: the discovery, then the generalized rule adopted from it.

Re-running the KV byte probe at `past_len=512`, a worker lost the Vulkan device (`VK_ERROR_DEVICE_LOST`), ORT silently rebuilt the session CPU-only and retried, and the process **exited 0** with a complete, well-formed counters file — `compute_calls 1, compute_failures 1, dispatches_executed 0` — which differenced against a healthy point as an apparent **6.7% KV saving that was in fact an observation ending early** (negative bytes were visible before the guard existed). Existing guards checked that the *observation* happened, never that the *work* did. Three refusal guards landed (`compute_failures != 0`, `compute_calls < iters`, `dispatches_executed == 0`), and the incident was generalized to a durable counter: `device_losses`, emitted at zero because a probe cannot refuse on a key that only appears once the failure has happened; any harness reading device counters now refuses (never differences) a point with `device_losses != 0`, and every harness calls `sess.disable_fallback()` so ORT's silent CPU retry cannot manufacture a false success. A failure-text classifier tested only on strings the author wrote matched none of the driver's actual wording (`"The logical device has been lost"`) and fell through to the wrong bucket — tested and fixed against the verbatim text. Attribution checked rather than assumed: the pre-fix binary on `main`, stashed and rebuilt, loses the device on the same workload — the loss is a property of the box under contention, not of the input-cache change being shipped.

### 2026-08-02T22:37:04-07:00: Switch — a declared push-constant range that is only partly written is undefined input, and padding beats shrinking because the pipeline cache is keyed without a push size

**By:** Switch (`switch-declared-push-constant-range-must-be-fully-written`). Best-Practices validation (Trinity's technique) surfaced six distinct `vkCmdDispatch()` warnings — shortfalls `{4,20,36,72,88,104}` against a declared 128-byte push-constant range — across 355 dispatches on both devices. Not a VUID and not a risk to criterion 3(a), but unwritten push-constant bytes are undefined, not zero: correctness today rests on no shader happening to read past the range it declares, which breaks the moment any shader grows a field. Fix: every recorder now writes the full 128 bytes, zero-padded, unconditionally — chosen over shrinking the declared range per-kernel because `pipeline.rs` keys its pipeline cache on `(shader, spec_constants)` with no push size, so a narrower per-kernel range would need to join that key or silently desynchronize into a hard error. Verified with a two-part liveness+sensitivity probe (a bare `push_constant_lines: 0` is equally consistent with "fixed", "the messenger is dead", and "validation was never armed"): 6→0 shortfalls on a different DLL hash pre/post fix, both devices, correctness re-confirmed via the CPU-EP comparison tests. A control asserting the exact prior count (14) rather than `> 0`/`!= clean` would have gone red on this legitimate improvement — recorded as a general rule: a falsifier that pins the exact value of a number it does not own converts a fix into a false regression.

### 2026-08-02T22:37:04-07:00: Morpheus — a proof is a property of a form *on a device*, not one bit answering two questions; `PROVEN` / `PROVEN-ELSEWHERE` / `UNPROVEN` replaces the false per-device-vs-device-independent dichotomy

**By:** Morpheus (`morpheus-a-proof-is-a-form-on-a-device`). Ruling on Link's ledger-toolchain finding (above): the device fail-open is R12 (no new rule needed) and the remedy is three states — `PROVEN` (device matches), `PROVEN-ELSEWHERE` (proven, but on another device — **claimable on purpose, but counted, disclosed and named**, since today that extrapolation already happens silently on every non-`device0` run and is indistinguishable from a same-device proof in every artifact), and `UNPROVEN`.
